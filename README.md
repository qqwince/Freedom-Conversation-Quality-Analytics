# Freedom Conversation Quality Analytics (CQA)

Прототип оценки качества диалогов операторов для хакатона Freedom Broker:
настраиваемый чек-лист, автоматическая оценка RU / KZ / EN диалогов с объяснениями
и ссылками на реплики, апелляции и решение проверяющего.

Команда **NOMADS**. Модель — DeepSeek V4.1 Flash (`deepseek-flash`) через внешний API,
запасная — `deepseek-v4-pro`; стоимость — в разделе [«Модель и стоимость»](#модель-и-стоимость).

## Как устроена оценка

```
диалог → подготовка (номера реплик, системные события, паузы)
       → промпт из чек-листа → DeepSeek → JSON с ответами, подпунктами, доказательствами
       → проверки кодом (повтор запроса при ошибках) → голосование
       → расчёт баллов кодом → результат с журналом вызовов модели
```

Модель отвечает только на вопросы чек-листа. Баллы, перераспределение N/A и округление
считает код (`backend/cqa/scoring.py`), поэтому итог воспроизводим.

## Быстрый старт

Нужен Python 3.11+.

```bash
python -m venv .venv
```
```bash
.venv/Scripts/python -m pip install -e ".[dev]"
```

Скопируйте `.env.example` в `.env` и заполните `CQA_API_URL` (ссылка GET из задания)
и `DEEPSEEK_API_KEY` (platform.deepseek.com → API keys). Можно работать и на Gemini:
`CQA_LLM_MODEL=gemini-3.5-flash` и `GEMINI_API_KEY` — провайдер выбирается по имени модели.

Запустить сервер и открыть интерфейс на http://localhost:8000/:
```bash
.venv/Scripts/python -m uvicorn cqa.api:create_app --factory --port 8000
```

Загрузить DEV-набор:
```bash
.venv/Scripts/python scripts/fetch_dataset.py
```

Контрольный набор — тот же адрес с другим `group_id`:
```bash
.venv/Scripts/python scripts/fetch_dataset.py --group-id <ID>
```

Оценить диалоги:
```bash
.venv/Scripts/python scripts/evaluate.py --ids p1-ru-001 p1-kz-001
```
```bash
.venv/Scripts/python scripts/evaluate.py --lang KZ --limit 5 --votes 3
```

Результаты: `eval/runs/<run_id>/<conversation_id>.json` — ответы, баллы, объяснения,
доказательства, пометки «требует проверки» и журнал вызовов модели.

## Интерфейс

После запуска сервера интерфейс открывается на http://localhost:8000/.

| Раздел | Что делает |
|---|---|
| Дашборд | KPI качества с целями, соблюдение каждого критерия и «сколько баллов даст его исправление», распределение итогов, все грубые ошибки с причинами, линии, рейтинг операторов и сводка для каждого |
| Чат-наставник | на странице оператора: вопросы «за что сняли баллы и как исправить» — ответ по правилам чек-листа и обоснованиям оценок именно этого оператора; посторонние темы отклоняются; 30 вопросов в день, в модель уходят только последние 6 реплик |
| Автообновление | администратор задаёт group_id и интервал: сервер сам запрашивает API организаторов, находит новые conversation_id, загружает и оценивает их; в шапке — «+N новых» |
| Моя сводка | для оператора: средний балл, место среди коллег линии, 2–3 пункта «над чем поработать» с честным расчётом роста балла; текст формулирует модель, без неё — шаблон |
| Диалоги | список с фильтрами (язык, канал, «требуют проверки», «грубая ошибка»), загрузка набора по `group_id` и своего транскрипта, пакетная оценка с прогрессом |
| Карточка диалога | итог и секции, критерии с ответом, баллами и весом; объяснение, доказательства и проверенный участок; клик по доказательству раскрывает диалог и подсвечивает реплику; у звонков — плеер с переходом к моменту реплики; апелляция по критерию; «Исходная / После апелляции»; журнал вызовов модели |
| Апелляции | очередь проверяющего: спорная оценка, комментарий, обоснование модели и фрагмент диалога; «Подтвердить» или «Изменить» с обязательной причиной; «Второе мнение ИИ» — модель заново проверяет только спорный критерий с учётом довода апелляции и говорит, подтверждается ли он репликами (подсказка: решение и причину вводит проверяющий) |
| Чек-лист | редактор критериев (тип, вес, шкала, N/A, подпункты для модели), версии; «Применить к диалогам» переоценивает моделью только изменённые по смыслу критерии, а при смене веса пересчитывает итог без модели |
| Создать с помощью ИИ | в редакторе чек-листа: вводите название, описание и вес — модель предлагает тип ответа, шкалу, правило N/A, подпункты проверки и правило решения по образцу текущих критериев; черновик сохраняется только после проверки администратором |

**Роли и отделы без паролей** (в ТЗ: «регистрация и вход в систему не нужны»). В шапке выбирается
демо-пользователь, сервер применяет его права (`backend/cqa/org.py`, `config/org.demo.json`):

| Роль | Права |
|---|---|
| Оператор | свои диалоги, «Моя сводка» и чат-наставник, подача апелляций |
| Проверяющий | очередь апелляций, решения, второе мнение ИИ |
| Руководитель | диалоги, дашборд и апелляции своих линий (одной, нескольких или всех) |
| Администратор | всё, включая чек-лист, загрузку наборов, автообновление и выгрузку results.json |

Отдел определяется по языку линии, оператор — по имени из приветствия: в данных организаторов
нет ни отделов, ни ID операторов.

**Темы:** тёмная, светлая и высококонтрастная (кнопка в шапке).

**Языки интерфейса:** RU / KZ / EN (переключатель в шапке). Переводятся подписи интерфейса;
переписка, объяснения модели и ответы по подпунктам остаются как есть.
Если в системе включено «уменьшение движения», анимации отключаются.

Результаты прогона из командной строки можно показать в интерфейсе:
```bash
.venv/Scripts/python scripts/import_run.py eval/runs/<run_id>
```

**Встраивание в Dynamics 365.** Интерфейс — чистые HTML, CSS и ES-модули без сборки (`frontend/`).
Компонент монтируется в элемент `<div data-cqa-app data-api-base="https://…">`: в `data-api-base`
указывается адрес сервера оценки. Все стили изолированы под классом `.cqa-app`, цвета и шрифты —
переменные в `css/tokens.css`, маршруты — по `#hash`, поэтому страницу можно загрузить как HTML web resource.
Во встроенном виде компонент не меняет оформление страницы-хозяина; фон всей страницы
красится только в отдельном режиме (`data-standalone` в `index.html`).

## Сдача результатов (results.json)

Формат — «Формат JSON 1.0» из приложения к гайду организаторов: `results/dev/results.json`
по DEV (65 записей) и `results/prod/results.json` по контрольному набору (ровно 10 записей).
Коды критериев (`contact`, `discovery`, …) берутся из поля `export_id` чек-листа, реплики
нумеруются с 1, N/A — `null`, неоценённый диалог — запись со `status: "error"`.

```bash
.venv/Scripts/python scripts/export_results.py --dataset DEV --team NOMADS
```

Выгрузка проверяет формат (все 8 критериев, допустимые значения, номера реплик, совпадение
`critical_flag`, уникальность ID) и не даёт сохранить файл с ошибками незамеченным.
Из интерфейса: «Диалоги» → «results.json».

### Час контроля: одна команда

При запущенном сервере `scripts/control.py` загружает набор из API организаторов, оценивает его,
повторяет неудачные диалоги, выгружает и проверяет `results/prod/results.json`, а с `--push`
сразу коммитит и отправляет файл. Всё видно и в интерфейсе.

```bash
.venv/Scripts/python scripts/control.py --group-id <ID> --push
```

После замены критерия («Чек-лист» → изменить → «Сохранить версию») переоценить только его:
```bash
.venv/Scripts/python scripts/control.py --group-id <ID> --criteria C9 --skip-import --push
```

Репетиция на DEV (`--group-id DEV --dev`, 08.11): загрузка 1 с, оценка 65 диалогов 249 с,
выгрузка и проверка < 1 с — **4,2 минуты**, ошибок 0. Десять контрольных чатов — около минуты.

Тот же путь вручную через интерфейс: «Диалоги» → «Загрузить набор» → выбрать все → «Оценить»;
затем `scripts/export_results.py --dataset <ID> --prod` и `git push`.

## Сервер API

Документация API: http://localhost:8000/docs. При первом запуске в базу (`data/cqa.sqlite3`)
загружаются исходный чек-лист и DEV-набор, если он уже скачан.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/datasets/import` | загрузить набор по `group_id` из API организаторов |
| POST | `/api/conversations/upload` | загрузить свой транскрипт (запись или ответ API) |
| GET | `/api/conversations` | список диалогов с последней оценкой, фильтры `dataset`, `language`, `channel` |
| GET | `/api/conversations/{id}/audio` | переход к записи звонка (свежая ссылка на mp3) |
| GET/PUT | `/api/checklists/{id}` | чек-лист; сохранение создаёт новую версию |
| POST | `/api/evaluations` | пакетная оценка в фоне; `criteria_ids` — переоценить только эти критерии |
| GET | `/api/jobs/{id}` | прогресс пакетной оценки |
| GET | `/api/evaluations/{id}` | результат; `?include_log=true` — с промптом и ответами модели |
| POST | `/api/evaluations/{id}/appeals` | подать апелляцию по критерию |
| GET | `/api/appeals?status=open` | очередь проверяющего: спорная оценка и комментарий |
| POST | `/api/appeals/{id}/decision` | подтвердить или изменить оценку с причиной |
| GET | `/api/evaluations/{id}/final` | исходная оценка, решения и финальный итог |
| POST | `/api/appeals/{id}/ai-opinion` | второе мнение ИИ по спорному критерию |
| POST | `/api/checklists/{id}/draft-criterion` | черновик нового критерия по названию и описанию |
| GET | `/api/export?dataset=DEV` | results.json в формате организаторов |
| GET | `/api/dashboard` | KPI, соблюдение критериев, распределение итогов, грубые ошибки, рейтинг |
| GET/PUT | `/api/sync` | настройки автообновления из API организаторов |

## Эталон и замер точности

```bash
.venv/Scripts/python scripts/gold.py status
```
```bash
.venv/Scripts/python scripts/eval.py --split tune --status draft --errors
```

`eval/gold/DEV.json` — наша эталонная разметка DEV: ответы по критериям, заметки к спорным
случаям, статус (`draft` — черновик, `verified` — проверено человеком) и часть `tune`/`test`.
На `test` (19 диалогов) промпт не подгоняется — это честная оценка точности.

Совпадение ответов с эталоном по критериям (`deepseek-flash`, один прогон на диалог, прогон 08.11):

| | чаты | звонки | всего |
|---|---|---|---|
| `tune` | 95,3 % (328 / 344) | 75,0 % (12 / 16) | 94,4 % |
| `test` | 93,4 % (127 / 136) | 56,2 % (9 / 16) | 89,5 % |

Слабее всего шкалы C4 и C6: модель промахивается на соседнюю ступень, причём в обе стороны.
Между двумя прогонами с одинаковыми правилами точность на `test` менялась на 3–4 пункта,
а голосование из трёх прогонов на `test` её не подняло (88,8 % против 88,8 %), поэтому по умолчанию
используется один прогон.

**Проверка эталона людьми.** Черновой эталон размечен моделью, поэтому слепая проверка командой:
```bash
.venv/Scripts/python scripts/gold.py review --split test
```
создаёт `eval/gold/review/test.md` (транскрипты и правила без ответов модели и эталона) и таблицу
`test.csv`; заполненная таблица принимается командой
`scripts/gold.py apply eval/gold/review/test.csv`, а проверенные диалоги получают `status: verified`.

## Ограничения

- Эталон DEV пока черновой (разметка модели), поэтому цифры точности выше — ориентир, а не гарантия.
- Звонки оцениваются тем же чек-листом по транскрипту; ошибки распознавания речи сказываются на
  C1 и C6, интонацию и дикцию мы не оцениваем. В контрольном наборе звонков нет.
- Подписи интерфейса переведены на KZ и EN, а названия новых критериев, созданных пользователем,
  остаются на языке, на котором их ввели.
- Хранилище — SQLite, оценки хранятся JSON-документами: для прототипа и демо этого достаточно,
  для промышленной нагрузки нужна серверная СУБД.
- Вход без паролей (так в ТЗ): роль выбирается в шапке, права проверяет сервер.

## Модель и стоимость

| | |
|---|---|
| Модель | `deepseek-flash` (DeepSeek V4.1 Flash), внешний API — в results.json `"mode": "external_api"` |
| Запасная | `deepseek-v4-pro` — только при перегрузке основной (`CQA_LLM_FALLBACK_MODELS`) |
| Вызовов на оценку | 1 (≈ 1,02 с учётом повторов при ошибках формата); с `CQA_VOTES=3` — 3 |
| Токены на диалог | в среднем ≈ 5,7 тыс. входных и ≈ 4,6 тыс. выходных (выход включает рассуждения) |
| Цена | $0,30 за 1 млн входных и $1,20 за 1 млн выходных токенов (часы пик) |
| **Стоимость одной оценки** | **≈ $0,007** в среднем, до $0,018 на самых длинных диалогах; DEV (65) ≈ $0,47, контроль (10) ≈ $0,07 |
| Время | ≈ 24 с на диалог; 8 параллельных запросов — DEV целиком за ≈ 4 минуты |

Цифры посчитаны по 196 полным оценкам из журнала (`usage` в каждой оценке хранит токены,
время и стоимость). В нерабочие часы DeepSeek берёт вдвое меньше.
