# План CQA (версия 3 — под критерии отбора)

## 0. Что изменилось

Главный критерий отбора — **точность AI-оценки на 10 новых транскриптах** относительно эталона
организаторов (Ground Truth). Поэтому:

- точность становится задачей №1, на неё работает отдельный человек всё время хакатона;
- появляется **свой эталон на DEV** и скрипт замера точности — без них качество не улучшить, только угадать;
- остальные критерии (функции, удобство, честность процесса, разнообразие архитектур) закрываем
  конкретными фичами из раздела 4.

| Критерий отбора | Вес для нас | Чем закрываем |
|---|---|---|
| Точность vs Ground Truth | **главный** | свой эталон, замер, сильная модель, подсказки из кода, голосование, разбор ошибок (раздел 2) |
| Функции и уникальность | высокий | уверенность и маршрутизация на проверку, дашборд точности, аналитика, аудио с переходом (раздел 4.1) |
| Удобство | высокий | путь «Импорт → Оценить → Карточка», прогресс, транскрипт рядом с результатом (раздел 4.2) |
| Корректность процесса | обязательный | журнал вызовов модели, кэш по хэшу текста, ручная загрузка транскрипта (раздел 3) |
| Разнообразие подходов | средний | облачная модель + локальная (Ollama) через один интерфейс (раздел 4.3) |

## 1. Что показали данные DEV

- 65 диалогов: 60 чатов (30 RU, 15 KZ, 15 EN) и 5 звонков (все RU, длинные: 45–115 реплик).
- Ролей 4: client 505, operator 339, bot 315, system 109 реплик.
- **Чаты по одному шаблону:** вопрос клиента → приветствие бота AIM → согласие на обработку данных →
  ответ бота → запрос оператора → `system: Эскалация на оператора` → оператор.
  Приветствие бота не засчитывается в C1 — модель должна это знать.
- **Темы повторяются в трёх языках** (тариф, пополнение, вывод, отчёты, облигации, вход в кабинет),
  но сценарии разные, не прямые переводы.
- **Системные события — готовые сигналы для критериев:**
  - C3: «Личность клиента подтверждена» / «Клиенттің жеке басы расталды» / «Customer identity verified»;
  - C7: «Оператор закрыл чат», «Клиент покинул чат», «Соединение с клиентом прервано», «Клиент завершил разговор» (и аналоги на KZ/EN);
  - звонки: «Клиент находится на удержании», «Запись приостановлена/возобновлена», перевод между агентами.
- **Звонки — шумный ASR:** искажённые фразы бота, имя оператора замаскировано `[Имя скрыто]`,
  запись прерывается. Оценивать по смыслу, а маскированное имя считать представлением.
- **`audio_url` — HTML-страница с плеером**, внутри `<audio src>` на mp3 с подписью, действующей ~1 час.
  Нужен бэкенд-эндпоинт, который при открытии карточки достаёт свежую ссылку на mp3.

## 2. Точность — главный трек

### 2.1 Свой эталон (gold) на DEV
- [ ] Разметить **все 60 чатов и 5 звонков** по чек-листу: ответ по каждому критерию, реплики-доказательства, итог.
  - Ускорение: модель делает черновик → человек проверяет и правит (≈2–3 мин на чат).
  - Делить между 2–3 людьми; 10 спорных диалогов разметить вдвоём и сверить — так находятся неясные места чек-листа.
- [ ] Хранить в `eval/gold/DEV.json` (коммитится — это наша работа, а не результаты контроля).
- [ ] Разбить на **tune (≈45)** для подбора промпта и **test (≈20)** для честного замера. На test промпт не подгонять.
  В test — пропорционально RU/KZ/EN и 1–2 звонка, как в контрольном наборе из 10.

### 2.2 Замер точности — `scripts/eval.py`
- [ ] Метрики:
  - точность ответа по каждому критерию (Да / Нет / N/A — точное совпадение);
  - шкалы C4, C6: точное совпадение ступени и средняя ошибка (MAE);
  - **MAE итогового балла** и доля диалогов с отклонением итога ≤ 5 баллов;
  - C8: precision / recall флага;
  - матрица ошибок «Да / Нет / N/A» — главный источник ошибок обычно N/A против «Да».
- [ ] Отчёт в консоль + `eval/reports/<дата>-<модель>-<версия промпта>.json`, чтобы сравнивать прогоны.
- [ ] Прогон после **каждого** изменения промпта или модели.

### 2.3 Модель
- [ ] Сравнить 2–3 модели на tune: сильная облачная (Claude Sonnet / GPT-4.1 / Gemini Pro),
  быстрая облачная (Haiku / mini / Flash) и локальная (Qwen2.5 / Llama 3.1 через Ollama).
- [ ] На контроле всего 10 диалогов — **берём самую точную**, даже если дорогая. Стоимость одной оценки — в README.
- [ ] `temperature = 0`, структурированный JSON-ответ по `schemas/llm_output.schema.json`.

### 2.4 Промпт
- [ ] Подпункты `checks` по каждому критерию (уже в `config/checklist.default.json`) — модель сначала отвечает на них, потом выводит ответ.
- [ ] Транскрипт с номерами и ролями: `[9] 01:15 operator: …`; бот и система помечены как контекст.
- [ ] Общие правила (`context_rules`) и правила доказательств (`evidence_rules`) — из конфига.
- [ ] **Короткие примеры (few-shot)** для трудных критериев — в конфиге критерия, поле `examples`,
  чтобы новый критерий на контроле тоже мог их получить.
- [ ] Варианты: один вызов на весь чек-лист или вызов на каждый критерий. Сравнить на tune:
  по критерию обычно точнее, но дороже; для 10 диалогов это неважно.

### 2.5 Подсказки и проверки из кода (детерминированные)
- [ ] **Перед вызовом модели** код вычисляет и передаёт в промпт как факты:
  - индекс первой реплики оператора;
  - системные события по словарю на RU/KZ/EN (идентификация, закрытие чата, уход клиента, обрыв связи);
  - паузы больше `wait_threshold_seconds` после первого ответа оператора;
  - был ли переход «бот → оператор» и что клиент успел сообщить боту.
- [ ] **После ответа модели** валидаторы:
  - индексы доказательств существуют, доказательство «оператор сделал X» — реплика оператора;
  - значение шкалы — одна из ступеней, N/A только там, где разрешён;
  - C3: если «Да», подтверждение личности должно быть раньше раскрытия данных;
  - C7: если «Нет», а после последней реплики оператора есть «Клиент покинул чат» / «Соединение прервано» — пометить «проверить N/A».
- [ ] При нарушении — повторный запрос с указанием ошибки, затем пометка «требует проверки».

### 2.6 Голосование и уверенность
- [ ] 3 независимых прогона, ответ по большинству; для шкал — медиана.
- [ ] Если прогоны расходятся — «низкая уверенность» по критерию (это же уникальная фича, раздел 4.1).
- [ ] Проверить на tune, даёт ли голосование прирост; если нет — оставить 1 прогон.

### 2.7 Цикл разбора ошибок
- [ ] После каждого замера — 3 критерия с худшей точностью → разбор конкретных ошибок →
  правка `checks`/`decision`/примеров в конфиге → повторный замер на tune.
- [ ] Финальный замер на test один раз перед контролем, цифры — в README и в презентацию.
- [ ] Ожидаемые трудные места: C2 (N/A против «Да»), C4 (ступени 15/10), C6 (ступени 10/7), C7 (N/A против «Нет»), звонки.

## 3. Корректность процесса (жюри проверит, что оценка настоящая)

- [ ] **Журнал оценки** в карточке: модель, версия промпта, версия чек-листа, время, токены, стоимость,
  полный промпт и сырой ответ модели (сворачиваемый блок).
- [ ] Кэш только по ключу `(хэш транскрипта, версия чек-листа, модель, версия промпта)` —
  никаких готовых результатов по `conversation_id`.
- [ ] **Ручная загрузка транскрипта** (вставить JSON или текст) — требование задания и доказательство работы на новых данных.
- [ ] Живой прогресс пакетной оценки: какой диалог сейчас обрабатывается.
- [ ] В README — раздел «Как убедиться, что оценка настоящая»: изменить реплику → переоценить → результат меняется.
- [ ] Результаты контрольного набора в репозиторий не класть; оценивать их на зафиксированной версии через UI.

## 4. Функции, удобство, архитектура

### 4.1 Функции и уникальные возможности (по убыванию ценности)
1. [ ] **Уверенность по критерию** и фильтр «требуют проверки» — человек смотрит только спорное.
2. [ ] **Дашборд точности** против своего эталона: точность по критериям и языкам — показывает зрелость подхода.
3. [ ] **Аудио:** свежая ссылка на mp3 через бэкенд, встроенный плеер, клик по реплике звонка → переход к моменту записи.
4. [ ] **Аналитика:** средний балл по критериям и языкам, самые частые нарушения, список диалогов с грубыми ошибками.
5. [ ] **Переоценка только изменённых критериев** после правки чек-листа + сравнение версий чек-листа.
6. [ ] Экспорт результатов в CSV / JSON.
7. [ ] Счётчик стоимости и времени оценки.

### 4.2 Удобство
- [ ] Основной путь в три шага: «Импорт по group_id → Оценить выбранные → Карточка».
- [ ] Карточка: транскрипт слева, критерии справа; клик по доказательству — прокрутка и подсветка реплики,
  наведение на номер реплики — всплывающий текст.
- [ ] Цвета: зелёный — Да, красный — Нет, серый — N/A, жёлтый — низкая уверенность, красная плашка — грубая ошибка.
- [ ] Итог крупно, под ним секции «набрано из максимума после перераспределения».
- [ ] Апелляция — кнопка у критерия; экран проверяющего — очередь, решение в один клик + причина.
- [ ] Интерфейс на русском, понятные пустые состояния и ошибки.

### 4.3 Разнообразие архитектур
- [ ] Один интерфейс `LLMProvider` с двумя реализациями: облачная модель и локальная через Ollama
  (OpenAI-совместимый API). Переключение в настройках.
- [ ] Замерить точность обеих на test и показать в README и презентации.
- [ ] Основной режим — тот, что точнее (скорее всего облачный).

### 4.4 Dynamics 365
- [ ] Чистый HTML/CSS/JS без сборки, изолированные стили (префикс `cqa-`), один `api.js` с `BASE_URL`.

## 5. Роли

- **A — бэкенд и LLM:** провайдеры, промпт, подсказки и валидаторы, голосование, журнал, аудио-эндпоинт.
- **B — фронтенд:** все экраны, переходы к репликам, плеер, апелляции, дашборды.
- **C — точность (весь хакатон):** эталон, `eval.py`, разбор ошибок, правки рубрик.
- **D — скоринг, README, демо:** модуль расчёта с тестами, вопросы организаторам, сценарий защиты; помогает C с разметкой.

## 7. Защита (5 минут)

1. **1 мин.** Интерфейс, импорт, выбранный диалог.
2. **2 мин.** Оценка, обоснования, переход к реплике, пример N/A, итог; журнал вызова модели; **цифра точности на нашем эталоне**.
3. **1 мин.** Апелляция → решение проверяющего → новый итог.
4. **1 мин.** Замена критерия и применение чек-листа к выданным диалогам.
