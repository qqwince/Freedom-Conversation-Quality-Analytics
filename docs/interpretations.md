# Трактовки чек-листа и вопросы организаторам

Решения, которые мы приняли там, где чек-лист допускает несколько прочтений.
Все они отражены в `config/checklist.default.json` (поля `checks`, `decision`, `na_rule`)
и меняются через редактор чек-листа без правки кода.

## Принятые трактовки

| # | Критерий | Ситуация | Наше решение |
|---|---|---|---|
| T1 | C1 | Приветствие бота | Не засчитывается: оценивается первая реплика **оператора**. |
| T2 | C1 | «Представился» | Достаточно имени **или** роли с компанией («специалист Freedom Broker»). |
| T3 | C1 | Язык клиента | По первым репликам клиента; если неясно — поле `language`. |
| T4 | C2 | Клиент всё сообщил боту | Это известные детали; переспрашивание — «Нет». |
| T5 | C2 | Данных хватало, оператор сразу ответил | N/A (а не «Да»). |
| T6 | C3 | Оператор запросил идентификацию, клиент её не прошёл, ничего не раскрыто | «Нет» — по памятке чек-листа: проверка требовалась и в чате не подтверждена. Если же диалог кончился раньше, чем дело дошло до данных счёта (оператор ещё уточнял детали), — N/A. Организаторы на вопрос не ответили. |
| T7 | C3 | Требовалась идентификация, подтверждения в чате нет | «Нет» (по памятке). |
| T8 | C3 / C8 | Данные счёта раскрыты без идентификации | C3 = Нет **и** C8 = Да (раскрытие конфиденциальной информации). Организатор на вопрос ответил: «Как вам кажется, этот кейс является нарушением обоих критериев?» |
| T9 | C4 | Нет внутренней базы знаний | Оцениваем по общим знаниям и согласованности; допущение пишем в объяснении. |
| T10 | C4 | Корректная эскалация или заявка | Считается «корректным следующим шагом» → может быть 20. |
| T11 | C5 | Шаблонное «извините за неудобства» | Не считается реакцией на конкретную проблему. |
| T12 | C6 | «Явное ожидание» | Оператор ушёл проверять информацию или пауза > 120 с после первого ответа (`wait_threshold_seconds`). Первая реакция не оценивается. |
| T13 | C7 | Чат закрыт системой без прощания оператора | «Нет», если до этого была возможность завершить. |
| T14 | C8 | Грубая ошибка и итог | Отмечается отдельно, итог **не обнуляется** (`critical_affects_total: false`). |
| T15 | Все | Звонки (5 шт.) | Применяем тот же чек-лист по транскрипту; интонацию и дикцию не оцениваем. |
| T16 | Итог | Округление | Только итог, до 2 знаков, ROUND_HALF_UP. |
| T17 | C1 | В звонке имя оператора замаскировано `[Имя скрыто]` | Считается, что оператор представился. |
| T18 | Все | Шум распознавания речи в звонках | Оцениваем по смыслу; ошибки ASR не считаются ошибками грамотности оператора (C6). |
| T19 | C7 | После ответа оператора — «Клиент покинул чат» / «Соединение прервано» | N/A, если у оператора не было возможности попрощаться; если была — «Нет». |

## Вопросы организаторам

1. **C3.** Оператор запросил идентификацию, клиент её не прошёл, данные не раскрыты — «Да» или «Нет»? (T6) — ответа нет, следуем памятке: «Нет».
2. **C3 / C8.** Раскрытие данных счёта без идентификации — только C3 = Нет или ещё и грубая ошибка C8? (T8)
3. **C1.** Засчитывается ли представление без имени («специалист поддержки»)? (T2)
4. **C1.** Клиент пишет на смеси языков (RU + KZ) — на каком языке должно быть приветствие? (T3)
5. **C6.** Какую паузу считать «явным ожиданием»? (T12)
6. **Звонки.** Применять к звонкам этот же чек-лист? Нужно ли оценивать дикцию и интонацию по аудио? (T15)
7. **C8.** Грубая ошибка — только отдельная отметка или итог обнуляется? (T14)
8. **Данные.** Будет ли у контрольного набора тот же формат и другой `group_id` в той же ссылке?

После ответов обновить таблицу и конфиг.
